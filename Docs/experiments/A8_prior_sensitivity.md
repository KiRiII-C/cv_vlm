# A8 — чувствительность повторной локализации к начальному пространственному prior

**Дата:** 2026-11-02.  
**Ветка:** `experiments/rtabmap-geometry-a0-20261031`.  
**Состояние:** `THREE_FULL_REAL_TRIALS_PASS / POSTHOC_GT_RELATIVE_METRICS_PASS / ABSOLUTE_CROSS_SESSION_MAP_ACCURACY_NOT_VALIDATED`.  
**GitHub Actions:** [run 41451763476](https://github.com/KiRiII-C/cv_vlm/actions/runs/41451763476).

## Научный вопрос

A7 подтвердил распознавание прежней карты на **двух независимых реальных RGB-D-записях**: `fr1/desk` (595 уникальных синхронизированных пар) и `fr1/desk2` (639 пар). Но этот эксперимент запускал RTAB-Map с `RGBD/StartAtOrigin=true`, а значит, внутреннее начальное предположение соответствовало **первой позе карты**. Требование пользователя — локализоваться после рестарта без подсказок. Нужно установить, насколько результат зависит от такой информации.

### Проверка первоисточника

В `rtabmap/corelib/src/Rtabmap.cpp` при выключенном инкрементальном картировании выполняется загрузка оптимизированных поз и сохранённой локализации. Если `RGBD/StartAtOrigin=true`, `lastPose` устанавливается в первую позу карты, затем используется как `_lastLocalizationPose`. При `StartAtOrigin=false` используется сохранённая последняя поза. Следовательно, обе инициализации **имеют пространственный prior**, но различный. В `rtabmap_ros/rtabmap_slam/src/CoreWrapper.cpp` параметр `initial_pose` передаётся `rtabmap_.setInitialPose()`. `Transform::fromString` принимает формат `x y z roll pitch yaw`.

### Строго контролируемое вмешательство

| Режим A8 | Инициализация | Ожидаемый смысл |
|---|---|---|
| `first_node` | `StartAtOrigin=true` | Априорная поза = первый узел карты (как A7) |
| `saved_last` | `StartAtOrigin=false` | Априорная поза = последняя сохранённая локализация |
| `wrong_8m` | `StartAtOrigin=true`, `initial_pose="8 0 0 0 0 3.141593"` | Контролируемо неверная поза +8 м и разворот 180° |

Между вариантами **не изменяются** RTAB-Map-параметры visual registration, map features, входной RGB-D поток, порядок кадров или способы подтверждения обработки. Для каждого варианта в отдельном процессе пересоздаются visual odometry и SLAM; карта загружается из **идентичной побайтовой копии** исходной SQLite, хеши SHA-256 фиксируются **до начала новой сессии**.

В каждой сессии воспроизводятся **все 639 RGB-D-пар** отдельной записи TUM `desk2` с подтверждением обработки каждого кадра через `OdomInfoLite`. Исходная карта строится один раз, по полным 595 парам `desk`. Никаких эталонных TUM-поз в SLAM и никакого повторного использования изображений `desk` для запроса.

## Метрики и критерии

Анализатор собирает `/info`, `/localization_pose`, `map→odom` TF и `OdomInfoLite`, а также:
- первый исходный индекс кадра с **принятым** global/proximity соответствием прежней карте;
- число уникальных событий с `loop_closure_id > 0` или `proximity_detection_id > 0`, исключая арифметическое двойное считывание событий двух типов;
- число сообщений `localization_pose`, кадры с `OdomInfo.lost`, число подтверждённых RGB-D-пакетов;
- проверку, что ID принятых совпадений действительно присутствуют в сохранённой карте;
- начальное `map→odom` смещение и его значение при первом принятом совпадении; это **диагностика prior, а не метрическая GT-ошибка**;
- наличие в логах факта применения `initial_pose` для `wrong_8m`.

**Методологическая защита:** если RTAB-Map не находит прежнюю карту при неверном prior, это **отрицательный результат** A8, а не ошибка CI. CI должен завершаться с FAIL только при неполном наборе наблюдений, неверном порядке кадров, ошибках загрузки/параметров/монитора или некорректном сопоставлении событий с SQLite. В отчёте нельзя оптимизировать параметры распознавания после просмотра результатов, чтобы улучшить конкретный сценарий.

**Критерий научного подтверждения:** независимые 639 кадров получены и обработаны в каждом из трёх вариантов; каждое событие имеет обоснованное соответствие и определённую задержку локализации. Само появление TF до первого принятого совпадения **не считается успешной локализацией**.

### Аудит действительно сохранённого prior

В исходной SQLite `Admin.opt_last_localization IS NULL`, `Admin.opt_poses IS NULL`, `Admin.opt_ids IS NULL`. Значит, название `saved_last` в workflow **не соответствует фактическому состоянию этой конкретной базы**: сохранённой последней позы в ней НЕТ. При `RGBD/StartAtOrigin=false` журнал не содержит ни установки `initial_pose`, ни автоматического сообщения `Update map correction based on last localization saved in database` до совпадений. В исходном `Rtabmap.cpp` автоматическая установка map→odom по последней позе проверяет `!_lastLocalizationPose.isNull()`. Поэтому этот вариант является существенно более сильной проверкой релокализации **без сохранённой координатной подсказки**, чем ранее A7.

При этом не следует называть эксперимент строгим доказательством математически **uniform global localization без любых priors**: у RTAB-Map могут оставаться априорные вероятности в Bayes-фильтре, а метрика абсолютной позиции относительно внешнего GT не проверена.

### Согласованность глобальных поз после принятого визуального совпадения

Выгруженные `localization_pose` приведены к одному исходному `desk2` frame index по опубликованным timestamps. Сравнение без ICP и без GT: все позиции уже принадлежат **одной сохранённой координатной системе `map`**, поэтому это прямое расхождение трёх незалежных повторных запусков на идентичных кадрах.

| Пары экспериментальных режимов | Общих кадров с принятыми позами | RMSE разности глобальных координат | p95 расхождения |
|---|---:|---:|---:|
| `first_node` / `saved_last` | 14 | **0.02159 м** | 0.03995 м |
| `first_node` / `wrong_8m` | 15 | **0.01906 м** | 0.03703 м |
| `saved_last` / `wrong_8m` | 20 | **0.02268 м** | 0.04007 м |

Получены сходные **глобальные позы относительно сохранённой карты**, несмотря на радикально различающиеся условия инициализации, и в случае `saved_last` — на отсутствие сохранённой последней позы. Это сильное **функциональное свидетельство восстановления по внешнему виду** на независимой записи помещения. Расхождение между прогонами **не** показывает абсолютную метрическую ошибку относительно окружающего мира.

**Строгое ограничение:** только одна пара независимых сессий одной комнаты, по одному проходу на каждый режим; нет подтверждения статистической устойчивости, нет новых переставленных объектов, нет полной оценки метрики `localization_pose`. Отличия ранней первой привязки (кадр 0 или 42) при одинаковых настройках тоже могут отчасти зависеть от недетерминированного исполнения на CPU.

[GitHub Actions #41453821487](https://github.com/KiRiII-C/cv_vlm/actions/runs/41453821487), **SUCCESS**. Этот независимый анализатор **не перезапускал RTAB-Map** и не менял данные эксперимента: скачал точные артефакты завершённого A8 (run #41451763476) и извлёк `groundtruth.txt` исходной записи `desk2`. GT нигде не попадал в обработку visual SLAM. Вычисления сохранены в `a8_pose_agreement.json` и `a8_sparse_metric_report.json`; исходники: [inter-arm](../../scripts/evaluate_pose_agreement_a8.py), [GT-relative RPE](../../scripts/evaluate_sparse_localization_a8.py).

Поскольку две TUM-сессии могут использовать разные мировые координаты, внешнюю ошибку **абсолютного положения** в `desk`-карте нельзя измерить простым вычитанием `localization_pose` и GT `desk2`. Вместо этого вычислена gauge-invariant относительная ошибка для **соседних событий принятой глобальной локализации** в каждом запуске: `Delta_est=T_est_i^{-1} T_est_j`, `Delta_GT=T_GT_i^{-1} T_GT_j`; ошибка `Delta_GT^{-1} Delta_est`. Это не покадровая RPE: между публикациями локализации могут быть пропущены многие исходные кадры. Сами **639/639** кадров обработаны системой, но `localization_pose` возникает только при принятом соответствии.

| Метрическая оценка по TUM GT `desk2` | Первый узел | Без сохранённой позы | Неверная +8 м/180° |
|---|---:|---:|---:|
| Принятых поз с доступной GT | 26 | 25 | 25 |
| Соседних пар принятых поз | 25 | 24 | 24 |
| Относительная ошибка трансляции, RMSE | **0.06053 м** | **0.06975 м** | **0.06626 м** |
| Относительная ошибка трансляции, p95 | 0.15972 м | 0.17598 м | 0.17651 м |
| Относительная ошибка ориентации, RMSE | **3.25°** | **3.62°** | **2.88°** |
| Holdout: SE(3)-fit по первой половине принятых поз, RMSE координат на второй половине | **0.03091 м** (13 тестовых поз) | **0.03194 м** (13 тестовых поз) | **0.03097 м** (13 тестовых поз) |

**Что подтверждено:** глобальные позы геометрически достаточно согласованы для восстановления местоположения в другом визуальном проходе, и результат сохраняется при сильном начальном смещении. Но ошибки **относительного движения между редкими событиями** порядка 6–7 см RMSE и до 8.69° максимум в одной из серий. Само межпрогонное совпадение поз на 2 см **не доказывает** точности карты в физическом пространстве.

**Что не доказано:** абсолютная точность `map→camera` в мировой системе координат, калибровка ковариации `localization_pose`, устойчивость при неизвестном расположении объекта, при реальном похищении робота или независимых условиях освещения. Holdout здесь лишь временное разделение одной query-последовательности, а не независимый датасет, поэтому нельзя считать его строгой внешней валидацией.

## Ограничения

- Даже при успехе всех трёх вариантов **строго prior-free локализация ещё не будет доказана**, поскольку `wrong_8m` использует намеренно введённое предположение, а остальные две ветви — встроенный prior.
- Возможно различие визуальной одометрии между запусками, поскольку все вычисления выполняются на CPU. По каждому варианту сохраняется полный набор диагностик.
- TUM GT-системы разных записей не принимаются за совпадающие без отдельной проверки; вычисление ATE для `/odom` в каждой отдельной сессии **не означает** глобальной ошибки `localization_pose`.
- Применимость к перемещённым объектам и динамической сцене на этих данных не проверяется.
- Нельзя приравнивать число принятых совпадений к количеству независимых мест в комнате: один и тот же узел может быть распознан неоднократно.
