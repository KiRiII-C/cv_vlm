# Этапы B — восприятие YOLOE, единые RGB-D измерения и краткосрочные ID

**Дата:** 2026-11-02. **Ветка:** `experiments/rtabmap-geometry-a0-20261031`.  
**Принятая декомпозиция:** B0 = общий геометрический контракт; B1 = реальные маски YOLOE → объекты в измеренном 3D; B2 = краткосрочный трекинг/семантическая неопределённость. **C** отвечает за долговременные физические UUID, перемещения и re-ID; **D** — обновляемый граф сцены; **E** — persistence/автономную релокализацию. Эти этапы намеренно не смешиваются.

## B0: общая обратная проекция RGB-D

**Код:** [shared_rgbd_geometry.py](../../src/semantic_map/shared_rgbd_geometry.py), [benchmark](../../scripts/b0_shared_geometry_full_tum.py), [tests](../../tests/test_shared_rgbd_geometry_b.py).  
**Реальный прогон:** [GitHub Actions #41455640452](https://github.com/KiRiII-C/cv_vlm/actions/runs/41455640452), **SUCCESS**, артефакт `b0-full-real-tum-shared-cloud`.

Контракт `SharedRGBDFrame` хранит единожды вычисленное организованное облако `H×W×3` в **оптической системе камеры**, карту валидности глубины, зарегистрированную глубину в метрах и **измеренную** `T_map_camera`. Модуль создаёт маскированные `Object3DObservation` с геометрией, локальной/глобальной центральной точкой, 3D AABB, исходными камерными точками и показателем валидной глубины. **ID маски, short ID треклета и долговременный physical UUID — разные сущности.**

`reproject_object()` повторно проектирует измеренные точки предыдущего объекта в новый кадр, вычисляет z-buffer, проверяет наблюдаемость через **текущую** depth. Состояния: видимое совпадение по глубине; за другим предметом (occluded); измеренный конфликт свободного пространства; неизвестный участок без depth. Вытеснение/удаление объекта **не доказывается** отсутствием 2D маски.

**Важные ограничения:** в B0 маска — явно обозначенная *несемантическая область по измеренной глубине*, а не YOLO. Поэтому низкий IoU этой области при повторной проекции (~0.017) **не измеряет качество распознавания объектов**; во входных точках используется прореженная выборка, и IoU для неё нельзя считать метрикой объектного tracking. Сравнение общего облака с одной старой проекцией одной маски **не доказывает ускорение всего конвейера**; выигрыш возникает при многократном использовании общего буфера большим числом масок и алгоритмов. **Повторное использование нативного GPU облака именно внутри RTAB-Map ещё не интегрировано** — B0 валидирует общий Python интерфейс как прототип.

## B1: настоящая YOLOE сегментация и 3D объекты

**Код:** [b1_yoloe_full_tum.py](../../scripts/b1_yoloe_full_tum.py), [CI](../../.github/workflows/b1-yoloe-shared-tum.yml).  
**Запуск:** [GitHub Actions #41456143947](https://github.com/KiRiII-C/cv_vlm/actions/runs/41456143947).

Сенсорный RGB-D поток: **595 из 595 кадров** обрабатываются организованной глубиной, включая кадры без очередной YOLO инференции. **YOLOE-26s-seg.pt** в CPU-режиме запускается на каждом пятом кадре, все фактические детекции и их confidence учитываются в отчёте. Детектированные маски фильтруются измеренной глубиной и преобразуются в `Object3DObservation` с A6-корректированными RTAB-Map позами. **GT-позы TUM для SLAM/3D-проекции не используются.** Между детекциями прогнозируется только видимость предыдущих 3D-точек относительно текущей depth; это **не подставляемая детекция и не доказательство сохранения объекта**.

Почему 26s, а не 26x: на CPU GitHub Actions это стартовая проверка интерфейсов и измерительной цепочки, не сравнительный тест качества модели. Оценка YOLOE-26x в целевой среде RTX4060 и поиск оптимальной частоты B2 — отдельная экспериментальная приёмка. Утверждение «обработаны все 595 RGB-D» означает полноту сенсорной геометрии, **не** 595 вызовов YOLO.

## B2: краткосрочное сопоставление без дополнительной tracking-нейросети

**Код:** [short_term_semantics_b.py](../../src/semantic_map/short_term_semantics_b.py), [tests](../../tests/test_short_term_semantics_b.py).

Используется существующий `TemporalTracker` с one-to-one Hungarian, 3D близостью, 2D bbox/mask и HSV appearance, с двухэтапным rescue низких confidence. Новый адаптер `ClassTolerantTemporalAssociator` вводит ограниченную и **явно проверяемую семантическую иерархию**, например `office chair` и `desk chair` → `chair` при сохранении исходных названий в evidence. Для несовместимых классов, например chair/table, сопоставление не разрешается. Семантическая память short-track содержит псевдосчётчики классов со сглаживанием Dirichlet; **эти числа нельзя считать калиброванными вероятностями физической идентичности** без эталонной разметки.

В B1/В2 сохраняются: исходные временные detection ID, короткий track ID, распределение исходных классов, количество tentative/confirmed/unresolved и фактический reprojection IoU/совпадение глубины. Эти признаки в B1 пока **диагностические**; вводить репроекцию как дополнительный жёсткий tracking gate без честного сравнения на размеченных физических ID пока нельзя.

## B2: полный количественный тест краткосрочной идентификации по физическому GT

**Код:** [b2_hypersim_short_track_gt.py](../../scripts/b2_hypersim_short_track_gt.py). **Реальный запуск:** [GitHub Actions #41457122979](https://github.com/KiRiII-C/cv_vlm/actions/runs/41457122979), **SUCCESS**, артефакт `b2-short-track-real-YOLOE26x-300-physical-GT`.

Использованы существующие **замороженные реальные предсказания YOLOE-26x**, сохранённые из независимого [полного 300-кадрового эксперимента #40820074555](https://github.com/KiRiII-C/cv_vlm/actions/runs/40820074555). Для **каждой из 3 сцен** используются **все 100 последовательных кадров**, GT instance ID — только для scoring. В 3D измерениях использовались **официальные Hypersim XYZ**. Эти результаты **не** проверяют A6 RTAB-Map-позы и не оценивают совместную ошибку SLAM+трекера.

Фиксированный набор гипотез: `3d_only` (3D центры и класс), `3d_and_appearance` (те же + маскированный HSV). Оба варианта используют ровно те же предсказания. В сохранённом artifact **не было настоящих 2D bbox/mask**, поэтому их влияние в этом сравнении **специально отключено**: никакой синтетический 2D bbox не использован для оценки score. Сравнение относится к частному 3D-only short tracker, **не** полной масково-проекционной системе.

| Размеченная физическими ID сцена | Только 3D IDF1 | 3D + appearance IDF1 | Ложные объединения 3D → 3D+appearance |
|---|---:|---:|---:|
| `ai_002_001` (разнообразная мебель) | 23.01% | **25.63%** | 2 → 3 |
| `ai_005_001` (похожие стулья) | 1.99% | **2.74%** | 0 → 0 |
| `ai_017_001` | 35.39% | **35.86%** | 6 → **10** |
| **Pooled (по IDTP/IDFP/IDFN, не среднее сцен)** | **13.59%** | **14.50%** | — |

Pooled GT-based counts:
- 3D only: **IDTP 545, IDFP 865, IDFN 6067**;
- 3D + appearance: **IDTP 582, IDFP 832, IDFN 6030**.

При этом `IDF1` рассчитывается для ассоциированных YOLOE-наблюдений с предварительным GT сопоставлением `IoU >= 0.10`, а пропущенные физические экземпляры включаются в denominator; это **не стандартная TrackEval/HOTA метрика с IoU>=0.5**. Фрагментация в сценах с похожими экземплярами очень велика и отсутствие обнаружений доминирует, поэтому переписывать только matcher недостаточно.

**B2 научный результат — NEGATIVE / PHYSICAL-ID-QUALITY-FAIL:** короткий трекинг с простой метрической близостью и HSV appearance не обеспечивает устойчивую физическую идентичность; нельзя на его основе без верификации присваивать стабильные `object_uuid` или переносить в сцену утверждение «это тот же объект».

## Критерии завершения всего B

- B0: полная реальная геометрия, совпадение с исходной обратной проекцией, latency (PASS).
- B1: реальный YOLOE inference + 3D-измерения на оптимизированных позах и полный учёт кадров (TECHNICAL PASS на 595 кадрах, 119 YOLO keyframes).
- B2: тесты класса/ID пройдены и выполнена первая физическая GT-проверка 300 кадров. **Физическая ID точность FAIL**. Полная mask+reprojection ассоциация с RTAB-Map и ablation частоты 3/5/10 на физических GT остаются NOT_TESTED.
- C и D не объявлять реализованными на основании коротких ID либо B0/В1 геометрии; перенос на физические UUID и события перемещений — отдельная валидация.

При последующих испытаниях запрещено искусственное сокращение RGB-D-последовательности. Частота YOLO / частота идентификатора — отдельный измеряемый **параметр**, а не прореживание сенсорного датасета.
